# Batch document-format support plan (pre-U10)

## Purpose
PaperBatch must let users add multiple supported documents to one run and render them into printable PDFs inside PaperBatch. LibreOffice may act as the conversion engine when explicitly configured. This is an in-app conversion path; it does not launch Microsoft Office or WPS and does not claim equivalent output fidelity. U10 real-user trials remain deferred.

## Current gap
Before BDF1, the production shell registered PDF pass-through and built-in JPEG/PNG rendering only. The repository had a hardened `LibreOfficeRendererAdapter`, but neither desktop production composition nor coordinator IPC registered it, and the adapter rejected Windows. The BDF1 implementation in this branch registers conversion when a trusted engine path and SHA-256 pin are configured, enables the supported conversion path on Windows and Linux, and keeps PDFium as the separate prerequisite for page inspection, composition and preparation. Unsupported or unconfigured documents remain unavailable for preparation and cannot silently fall back to another renderer.

## Unit BDF1 — production conversion and mixed-batch CI
- Register the existing LibreOffice adapter in both desktop and coordinator production renderer factories only when explicit engine-path and trusted SHA-256 configuration is present. Keep PDFium as the separately required PDF inspection/composition runtime. No auto-discovery, download, bundled proprietary app, WPS/Office launch, or silent fallback.
- Extend the direct-engine conversion path to Windows and Linux, with private per-operation profiles, macro/link protections, bounded source and final-artifact sizes, a two-minute process timeout, cancellation, monitored termination, and process cleanup. On Linux, `RLIMIT_FSIZE` is a kernel-enforced per-file limit; on Windows, the output monitor is best-effort and may allow temporary overshoot before stopping the process. Neither mechanism caps aggregate per-conversion profile/cache/temp storage. MacOS product conversion remains explicitly unsupported unless already safe and supported by the implementation.
- Make UI availability state explain whether document conversion is configured; unsupported/unavailable input must fail before any print submission.
- Exercise DOCX, XLSX, PPTX and OpenDocument/RTF fixtures through the same production batch preparation/import path. Assert order, persisted PDF artifact metadata, stable source identity, mixed PDF/image/document batches, conversion failures, no fallback, and no duplicate submission. Submit only to an injected fake spooler.
- CI must run on hosted Windows and Linux with a verifiably pinned LibreOffice engine and synthetic fixtures; report exact engine/tool versions, runner, scenario outcomes and evidence limits. Existing macOS CI remains a protocol/unsupported-platform lane, not PaperBatch macOS support. Never claim Office/WPS equivalence, human fidelity, driver compatibility, or paper output.

### Output and resource limits
The adapter limits each source and accepted final PDF artifact to 512 MiB and serializes conversions with an in-process semaphore plus an owner-only cross-process lock under the current user's PaperBatch data directory. This serializes PaperBatch conversion processes that share that per-user data root; it does not coordinate separate OS users or isolated data-root overrides. A conversion process has a two-minute timeout. Linux launches LibreOffice with a kernel-enforced `RLIMIT_FSIZE` of 512 MiB per file; this is not an aggregate operation quota. Windows polls the output file and terminates the owned process tree at the 512 MiB ceiling. Because the check is periodic, Windows may temporarily exceed that threshold; the final artifact is rejected if it exceeds 512 MiB. The monitor is not a hard disk cap. Neither platform currently enforces a total disk quota across the private profile, LibreOffice caches, and temporary files. Cancellation and timeout terminate and reap the owned process tree, then clean the operation directory. These controls are resource safeguards, not a sandbox or a strict total disk-usage guarantee.

### Accepted Windows limitation
The user accepted retaining the Windows best-effort output monitor for BDF1, with the limitation above recorded in product and CI evidence. This does not authorize a claim of a hard output or total-disk cap. The Linux per-file limit and Windows final-artifact check remain required. Microsoft Office/WPS applications, macOS product support, physical output, and U10 remain out of scope.
