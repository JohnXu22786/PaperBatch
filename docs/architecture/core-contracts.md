# Core model, state, schema, and IPC contracts

## Deterministic physical page layout

`PaperBatch.Core.Layout.LayoutCompiler` turns ordered rendered page dimensions into immutable physical-face mappings. It validates source IDs, page dimensions, page ranges, copies, N-up mode, fit mode, and an output-page budget before expanding copies. Page selection and reverse order are deterministic. Copy order is explicit (`CollatedPackets` or `PerDocument`); source-page identity and copy number remain separate fields. A placement retains its source page, N-up slot, target cell rectangle and dimensions, scale, and rotation decision. Covers, separators, and duplex blanks are tagged explicitly. Segment IDs combine the effective media/printer/tray settings with their contiguous run ordinal, so nonadjacent compatible runs remain separate jobs.

Duplex output maps each physical face in order and estimates sheets from the resulting faces. When `SeparateFilesOnFront` or `SeparatePacketsOnFront` is selected, an odd face boundary receives a blank back before the next front. These are logical estimates; printer-added sheets, jams, and physical output are outside this compiler. Scaling uses the selected media/sheet box and preserves proportions; `ActualSize` intentionally permits content outside that box. The layout does not claim a PDF artifact.

`IPageCompositionAdapter` is the only composition seam: it receives the exact immutable page map and writes to a caller-owned stream. `PdfiumPageCompositionAdapter` clones and transforms vector page objects through an explicitly configured PDFium runtime, then reopens and verifies the serialized output. PDFium generates a fresh trailer `/ID` value on each save, so byte determinism is defined over the complete PDF output except the two hexadecimal `/ID` string payloads; all other bytes and the ID array syntax must match, and repeated outputs must reopen and render identically. The Windows CI fixture validates this adapter against a digest-pinned community PDFium build; that build is not bundled or represented as an official Google/Foxit distribution. Product runtime distribution and qualification remain provisional, and interactive form support, Office/WPS interoperability, printer-driver behavior, GDI queue/job identity, and physical output remain unverified under G1. Preview and print must consume the same compiled map and prepared artifact.

This note defines the shared .NET 10 contracts introduced before UI, renderer workers, or a Windows print backend. Engine versions, document formats, PDFium ABI, and printer-driver settings remain behind later versioned adapters.

## Renderer adapter ownership

`RendererCoordinator` selects the first adapter that explicitly supports both a source format and execution context, invokes it once, and reports `Unsupported`, `Failed`, `TimedOut`, `Cancelled`, or `RequiresUserReview` distinctly. It never silently retries with another engine. Each adapter owns the processes and handles it creates. `OwnedProcessWorker` keeps the exact launched process handle, terminates only that process tree on timeout or cancellation, and waits for exit. Adapters must await that cleanup before completing; the coordinator waits for adapter cleanup after timeout or caller cancellation. This boundary contains crashes; it is not a security sandbox. Native Office and WPS adapters are restricted to a user initiated interactive desktop session. LibreOffice adapters must use an isolated profile created beneath an owner-only operation directory; Unix operation directories with group or other permissions and shared writable ancestors without the sticky bit are rejected; Windows ACLs are restricted to the current user. The profile disables macros and external-link updates and must not expose a UNO listener. A future concrete adapter must preserve the source snapshot and produce a stable PDF artifact.

## Prepared runs and renderer boundary

A `PreparedRun` is immutable after construction. It contains opaque snapshot IDs and SHA-256 values, renderer identity/version and capability contract version, rendered artifact identity/hash/page count, ordered source-to-rendered page mappings, effective print settings, and consecutive compatible segments. Settings include copies, color, duplex, media, orientation, and scaling, with optional opaque printer and tray IDs. It does not contain a source path, document bytes, or password. Segment flattening must cover every prepared item exactly once in the original order, and all items in a segment must have identical effective settings. Renderer capability media types are generic MIME identifiers; no engine or suite name is assumed by the core.

Prepared-run JSON v1 remains readable and round-trips as v1 for existing records that have no final artifact. New runs with a composed PDF use JSON v2 and include its content-addressed artifact ID, SHA-256, byte length, and page count. The PDF bytes remain in the private `RenderArtifactStore`; the run store persists only this identity. `PreparedArtifactCoordinator` snapshots sources, renders each immutable snapshot once, reads page geometry from the persisted renderer PDF, compiles the U4 layout in source order, writes and reopens the final PDF, then creates the durable run. A failure or cancellation creates no run. The coordinator requires an injected static-content verifier before composition. The production desktop supplies its configured PDFium inspector, which rejects pages with forms or annotations; unsupported or uninspectable content fails closed. The lower-level composition adapter does not independently inspect source content and requires this verifier result before composition.

Run state is an aggregate of its segment jobs. Each job records its own append-only transition history:

| Job state | Meaning |
|---|---|
| `Ready` | Prepared and durably recorded; no OS submission intent exists. |
| `InProgress` (run aggregate) | Segment jobs have different states; inspect per-job history for the exact outcome. |
| `Submitting` | Idempotent submission intent was committed before the OS side effect. A crash here is uncertain. |
| `AcceptedByOs` | The OS receipt/job identity was committed; acceptance does not mean processing or paper output. |
| `OsProcessing` | The OS reports the job is processing. |
| `OsReportsComplete` | The OS reports completion. This does not assert that physical pages came out correctly. |
| `FailedBeforeSubmit` | Failure is known to be before the external submission side effect. |
| `CancelRequested` / `CancelObserved` | Cancellation was requested / observed; neither means pages can be recalled. |
| `NeedsReviewUnknown` | The OS outcome cannot safely be inferred, such as the intent/receipt crash gap. No automatic retry follows. |
| `UserConfirmedPaperOutput` | A user explicitly confirmed the paper output. This is the only state that records physical-output confirmation. |

The state graph rejects backward transitions and allows `UserConfirmedPaperOutput` after OS completion, observed cancellation, or explicit operator confirmation while the OS outcome remains unknown. Direct confirmation from `NeedsReviewUnknown` preserves the prior uncertainty in transition history. Reconciliation out of `NeedsReviewUnknown` is explicit. The core makes no physical-success claim from a queue record or OS status.

## Windows print boundary

`WindowsPrintCapabilityEnumerator` performs read-only local queue and driver capability enumeration through Winspool. A queue identity binds the queue name, driver and port; the capability fingerprint binds that identity to the reported option inventory. Media and tray names and resolution values are preserved as driver tokens. Color and duplex are conservative: a color device does not imply monochrome support, and Winspool's boolean duplex flag does not prove which edge modes a driver accepts. Unsupported, unavailable and unknown capabilities therefore remain distinct, and an unknown option cannot pass job mapping. The current `PrintSettings` contract has no resolution or finishing selection fields; the capability inventory reports those values without substituting them for a requested setting.

`WindowsPrintCoordinator` accepts one prepared segment only after two matching capability reads and exact mapping of the selected media, tray, color and duplex values. It reads and verifies the final artifact referenced by the persisted `PreparedRun`, then passes that same PDF stream and identity with the request. It writes submission intent through `SqliteRunStore` before calling the backend. A matching receipt persists queue identity, OS job ID, per-attempt nonce, submission time and optional driver context. A replay of an intent without a receipt becomes `NeedsReviewUnknown` and is never automatically submitted again. Status and cancellation calls receive the complete persisted receipt so an implementation can scope native operations to that exact queue/job attempt. OS-reported failure after submission remains uncertain in the current state model; `FailedBeforeSubmit` is reserved for known pre-spool failures. Cancellation races preserve whichever durable state won first.

The `IWindowsPrintBackend` seam now has a production Windows Winspool/GDI implementation for rendering and submitting the exact persisted PDF artifact, plus deterministic fake tests. It verifies the artifact digest, bounds rasterization to 300 DPI and page dimensions, maps only fully identified driver capabilities, validates requested `DEVMODE` fields before `StartDoc`, returns the OS job ID, and scopes status/cancel requests to the queue and receipt. Failures after `StartDoc` remain ambiguous. Winspool cancellation requires a final job-title nonce check followed by `SetJob` with a numeric ID; the API has no atomic compare-and-cancel, so the remaining ID-reuse race is documented and the desktop UI is not wired to this backend. Hosted Windows CI only reads queue capabilities and must not submit to Microsoft Print to PDF or open its interactive save flow. The GDI document lifecycle, a validated driver route, queue/job correlation under real jobs, and paper output remain open G1 evidence. Neither fakes nor queue enumeration close G1.

## SQLite metadata store

`SqliteRunStore.Initialize` runs forward migrations in one SQLite transaction using `PRAGMA user_version`; it never downgrades a newer database. Version 1 created run, job, and transition tables. Version 2 adds retention-while-unresolved metadata and a unique submission idempotency key. Initialization runs `PRAGMA quick_check` after migration and may safely run again. It then removes expired runs through `DeleteExpiredRuns`; job and transition rows are deleted in the same transaction. `ExpiresAtUtc` is an absolute deadline supplied when creating the run; resolving the run does not change that deadline. Runs are retained past expiry while they contain a submitting, OS-accepted, processing, cancel-requested, or unknown-outcome job when `RetainWhileUnresolved` is set. Ready jobs have no OS-side effect and do not block cleanup. Passing `RetainWhileUnresolved: false` allows expired active or uncertain jobs to be removed by explicit policy.

Run creation stores prepared metadata in a schema-versioned JSON envelope, with a representative version-1 golden fixture at `tests/PaperBatch.CompatibilityProbe.Tests/Fixtures/prepared-run-v1.json`. `GetPreparedRun` validates the supported version and domain invariants before restoring the immutable model. Persisted job IDs are generated independently of segment IDs, so separate runs may reuse segment IDs. Run creation inserts the run, all segment jobs, and initial `Ready` transitions in one transaction. `BeginSubmission` atomically stores the idempotency key, `Submitting` state, and transition before the caller contacts the OS. `RecordOsReceipt` atomically stores the receipt and `AcceptedByOs` state. Replaying an identical key returns the original record; reusing it for a different request or receipt fails. A `Submitting` record without an OS receipt is intentionally ambiguous and must become `NeedsReviewUnknown` if reconciliation cannot find a trustworthy result.

The database stores hashes, opaque snapshot/artifact IDs, page/settings metadata, state, OS receipt identifiers, and retention timestamps. It has no document-content, credential, or password fields. Recipes may reference user-selected local locations, but the SQLite prepared-run record does not persist those locations.

## Source intake and snapshots

`SourceEnumerator` accepts explicit files and folders. Explicit selections keep their submitted order; files discovered under each folder use deterministic natural ordering, and recursion is opt-in. The configured entry limit counts each explicit selection before path probing plus discovered entries, and processing stops at the first over-limit selection after adding one limit diagnostic. Reparse points and device objects are reported and skipped, including when an explicit file or folder is beneath a linked ancestor, so a directory link, device handle, or provider-managed placeholder is never followed implicitly. Path aliases are compared after absolute-path normalization with Windows case-insensitive or Unix case-sensitive semantics. Duplicate selections stay visible with a `DuplicatePath` diagnostic; `SourceInput.IntentionalCopy` explicitly preserves repeated files or folder contents as additional copies. Each item carries its transient source path and path-free diagnostics. The path is not part of `SourceSnapshot`, `PreparedRun`, SQLite metadata, or normal diagnostic messages.

Preflight runs on the captured cache bytes. It recognizes PDF, JPEG, PNG, classic TIFF, RTF, legacy OLE Office, OOXML DOCX/XLSX/PPTX, and ODT/ODS/ODP. Signature and container checks are bounded: PDF checks its header, follows at most 64 `/Prev` links, and requires `startxref` to resolve to a cross-reference table or a cross-reference stream whose declared `/Index` records fit its complete body; FlateDecode xref streams are decoded within bounded limits, while unsupported filters and `DecodeParms` are rejected; encryption keys in any inspected trailer or cross-reference stream are detected. RTF password markers are recognized as control words across the bounded input, with escaped text and `\\binN` data skipped; a missing byte count or truncated binary segment is malformed. JPEG checks require a frame, scan data, and terminal marker; PNG chunk CRCs and raster dimensions are checked and the combined `IDAT` payload must be nonempty; TIFF checks directory structure, rejects duplicate tags, caps aggregate strip/tile array values across all directories, checks strip or tile ranges, and enforces raster dimensions. Legacy Office checks the compound-file allocation table and requires the expected Word, Excel, or PowerPoint stream directly under the root storage; FAT/DIFAT membership uses bounded set lookups, stream chains cannot overlap, and their combined traversal is bounded by the file's sector count. It checks bounded Word FIB flags and scans a bounded Excel workbook prefix for a `FILEPASS` record to identify common legacy password protection. Encrypted-package OLE files are diagnosed only when both `EncryptionInfo` and `EncryptedPackage` streams are present. ZIP packages validate central-directory size, entry names, local and central flags, methods, CRCs and sizes, data descriptors, encryption flags, compression ratios, and the expected document-family entries. DEFLATE entries must reach the final block exactly at the declared compressed-payload boundary; trailing bytes are rejected. OOXML packages require `[Content_Types].xml`, the root `_rels/.rels` relationships part, and the family document part. OpenDocument packages require `mimetype`, `META-INF/manifest.xml`, and `content.xml`; intake checks the uncompressed `mimetype` entry and reads the manifest only within the configured metadata limit to detect `manifest:encryption-data` without resolving external entities. Payload CRC and uncompressed length are verified by streaming entries through a bounded buffer; no extracted files are written. These checks identify obvious mismatches, truncation, encryption markers, and unsafe metadata; they do not establish full document conformance, accurate page counts, font/glyph coverage, or renderer compatibility. WPS-native formats remain unsupported.

`SourceSnapshotCache` writes to a configurable app-owned private directory, with owner-only Unix permissions and a current-user Windows ACL. Each capture uses a unique opaque ID, checks every path component for reparse points before and after opening the source, rejects device handles, copies while computing lowercase SHA-256, and compares the opened file identity, length, and last-write time before and after the read. File-identity query errors and cached read failures during preflight become per-item intake failures; rejected snapshots are released so one source cannot abort the rest of a batch. Windows uses handle-based file identity; Linux uses the verified x86-64 layout and reports an unsupported-architecture diagnostic on other Linux process architectures. Other platforms fail closed until equivalent no-follow and handle-identity checks are available. It flushes content and bounded metadata in an operation-specific temporary directory, then publishes the complete directory atomically. Quota and retention mutations use both an in-process gate and a cache-root file lock, so concurrent processes cannot exceed the shared byte or snapshot-count limits; a quota check reclaims validated orphan temporary directories left by interrupted captures and removes only regular files matching the cache-generated metadata-update temporary naming pattern during released-entry eviction. `OpenRead` verifies the cached bytes against the stored length and digest before returning a stream. Captures start retained, and callers release them only after all referencing runs are safely resolved. Quota cleanup removes only validated, released cache entries with no unexpected files. Snapshots are not deduplicated, and cache removal does not claim secure erasure.

Diagnostics use stable codes and constant, path-free messages. Missing and unreadable sources are reported per item; generic read failures may indicate a lock, provider, network, or transient failure, without claiming those states can always be distinguished. UNC paths, including extended UNC paths, are labeled as remote with provider availability unknown; local Windows device namespaces such as `\\?\C:\...` are not. Local cloud providers and file locks do not have a universal detection API, so an item may instead report a general unavailable-source diagnostic. These structural checks and synthetic fixtures are not native Office or rendering evidence and do not close G1–G4.

## Recipe JSON v2

Recipes use UTF-8 JSON with a required integer `schemaVersion`. The current schema is v2; the strict parser also reads v1 recipes. V1 remains a supported legacy shape without per-source overrides or setting rules; v2 adds those optional fields. Serialization preserves the recipe version, so a parsed v1 recipe can be read and serialized as v1, while newly created recipes use v2. Rules are evaluated in order and the first matching filename glob/source type supplies optional values; a per-source override is applied afterward. The resolver records the source of each effective value. The parser rejects comments, trailing commas, unknown properties, integer enum values, duplicate source IDs, invalid setting values, and unsupported schema versions. V2 rules have bounded counts and globs; recipes are limited to 256 KiB and 500 sources. The schema contains locations and settings only; it has no scripts, regular expressions, or embedded documents. Property ordering, indentation, and enum tokens are stable; the v1 shape has a golden serialization fixture at `tests/PaperBatch.CompatibilityProbe.Tests/Fixtures/recipe-v1.json`, and compatibility tests cover v2 rule and override resolution and round-trip.

## Local coordinator IPC v1

Requests and responses carry protocol version `1` and a correlation ID. Requests also carry an operation, optional idempotency key, and JSON object payload. Unknown properties and protocol versions fail closed. Request and response messages are limited to 256 KiB; error codes and messages are bounded. Capability negotiation chooses the highest shared version and the smaller peer message limit.

`NamedPipeCoordinatorServer` and `NamedPipeLocalCoordinatorTransport` implement the local byte-stream transport. Each frame has a four-byte little-endian length prefix; zero, oversized, truncated, malformed, and unsupported-version frames fail closed. The server uses `PipeOptions.CurrentUserOnly`, limits simultaneous clients, negotiates the protocol and maximum payload before dispatch, and checks response correlation IDs. Clients use bounded connection/request deadlines. `CoordinatorInstanceLease` uses an exclusive owner-only lock file below the current user's local application data directory to prevent two host processes from owning the coordinator at once. Desktop and CLI launch the same Core host in a dedicated process on demand when the pipe is absent. The client waits up to ten seconds for startup and returns a nonzero unavailable result if the host cannot be reached. The host owns the existing durable run store, preparation coordinator, content-addressed artifact store, and Windows print coordinator; desktop preparation, submission, status refresh, and cancellation flow through that service. No network listener or service installation is used.

The CLI `watch <folder>` command performs one bounded authoritative scan through the existing `WatchFolderScanner` and `WatchFolderProcessor`, waits for a two-second stable observation, then delegates supported stable PDF/JPEG/PNG candidates to the shared preparation coordinator with content-hash idempotency. Prepared runs remain for explicit user review; watch never submits automatically. Office/WPS and other unsupported candidates are reported as review-required. The command does not install a background monitor or persist a watch rule.

## Verification boundary

The Linux and Windows CI matrix builds this library and runs the unchanged U0 tests together with focused core regression tests. None of those tests closes G1. Native Office/WPS, PDFium behavior, Windows spooler/driver routing, and verified physical output remain pending until the native evidence is recorded in the compatibility matrix.
